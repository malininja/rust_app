# Warehouse Stock Module

**Date:** 2026-03-26

## Purpose

Track how much of each article is currently in the warehouse. Stock levels are maintained in a dedicated `warehouse_stock` table and updated whenever a goods receipt or invoice is confirmed.

## Approach

### Database

New table `warehouse_stock`:
- `article_id UUID PRIMARY KEY REFERENCES articles(id)` — one row per article; used as the PK for the upsert conflict target
- `quantity NUMERIC(12,4) NOT NULL DEFAULT 0` — running balance, matches precision of existing items tables
- Standard `created_at` / `updated_at` timestamps with `on_update_timestamp()` trigger

Stock is modified via an upsert (`INSERT ... ON CONFLICT (article_id) DO UPDATE`) passing a positive delta for goods receipts and a negative delta for invoices.

### New `warehouse` Module

Follows the standard layered architecture (`model → repository → service → handler → router`). Provides two read-only endpoints:

- `GET /warehouse` — all articles with their current stock quantity
- `GET /warehouse/{article_id}` — stock for a specific article (404 if never received)

Both endpoints require authentication (`logged_in` middleware).

### Confirmation as a Dedicated, Irreversible Action

`confirmed` is removed from the update DTOs for both `goods_receipts` and `invoices`. Confirmation is handled by a separate endpoint on each module:

- `POST /goods_receipts/{id}/confirm`
- `POST /invoices/{id}/confirm`

The repository `confirm` method uses `WHERE confirmed = false` in the UPDATE, so it only fires once — calling it a second time returns no rows (→ `409 Conflict`). It is not possible to un-confirm a document.

When a goods receipt is confirmed, each item's quantity is added to warehouse stock. When an invoice is confirmed, each item's quantity is subtracted.

### Cross-Module Integration

The `goods_receipt_service::confirm` and `invoice_service::confirm` functions each take two repository parameters: the module's own repo and a `PgWarehouseRepository`. The corresponding handlers construct both from `app_state.pool`.

New error variants added to both error enums:
- `AlreadyConfirmedOrNotFoundError` → handler maps to `409 Conflict`
- `StockUpdateError` → handler maps to `500 Internal Server Error`

## Key Rust Concepts

- `ON CONFLICT` upsert for accumulating a running total in a single SQL statement
- `WHERE confirmed = false` in UPDATE as an atomic idempotency guard
- Passing multiple repositories to a service function
- `rust_decimal::Decimal` for precise numeric arithmetic

## Known Limitation

The document confirmation and the warehouse stock upsert are two separate database writes (not wrapped in a single cross-repository transaction). In a failure scenario, a document could be confirmed but the stock update skipped. Acceptable for current scope.
