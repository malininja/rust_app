# Feature: Repository Pattern + Unit Tests for Roles Module

**Date:** 2026-03-04

## Goal

Refactor `role_service.rs` to follow the **repository pattern** by extracting database access into a `role_repository.rs`, then write unit tests for `role_service.rs`.

---

## Current State

- `src/roles/role_service.rs` — contains `get_all_roles`, which queries the DB directly via `sqlx`
- `src/roles/role_model.rs` — defines `RoleModel`
- `src/roles/role_handler.rs` — calls `role_service::get_all_roles` with a `PgPool`
- No repository layer, no unit tests

---

## What Needs To Be Done

### 1. Create `src/roles/role_repository.rs`

Extract the raw SQL query from `role_service.rs` into a repository module. The repository is responsible for all direct database interactions.

**Suggested function signature (in plain terms):**
- A public async function `get_all` that takes a `&PgPool` and returns `Result<Vec<RoleModel>, sqlx::Error>`
- Move the `sqlx::query_as!` call from `role_service.rs` into this function

### 2. Refactor `role_service.rs`

The service should delegate to the repository instead of querying the DB directly.

- `get_all_roles` should call `role_repository::get_all(pool)` internally
- The service layer is where business logic would live — for now it's a thin pass-through, but the separation matters for testability

### 3. Register the new module

Add `pub mod role_repository;` to `src/roles/mod.rs`.

### 4. Write Unit Tests for `role_service.rs`

Because `role_service.rs` currently takes a `&PgPool` directly, testing it without a real database requires making the dependency injectable. Two common approaches:

**Option A — Trait-based abstraction (recommended for learning)**
- Define a `RoleRepository` trait with an async method `get_all`
- Implement it for a real struct that wraps `PgPool`
- In tests, implement it on a mock struct that returns hardcoded data
- Key crates/concepts: `async_trait` (for async methods in traits), `mockall` (optional, for auto-generating mocks)

**Option B — Function injection**
- Pass the repository function as a parameter to the service function
- Simpler but less idiomatic for growing codebases

The feature doc recommends **Option A** as it teaches important Rust patterns: traits, generics, and how Rust approaches dependency injection.

---

## Key Rust Concepts Involved

- **Traits** — defining shared behavior (`RoleRepository` trait)
- **`async_trait`** — the `async_trait` crate, needed because async functions in traits aren't yet stable in all contexts
- **Unit testing** — `#[cfg(test)]` modules, `#[tokio::test]` for async tests
- **Dependency injection** — passing behaviour as a trait object or generic bound instead of a concrete type
- **Module system** — `mod`, `pub mod`, `use` paths across files

---

## Relevant Crates

- `sqlx` — already in use
- `async-trait` — needed for async methods in traits
- `tokio` — already in use; `#[tokio::test]` for async test runner
- `mockall` — optional, auto-generates mock implementations of traits
